# 0011: Isolated OpenCV board geometry

Status: accepted for CB-21.

## Decision

Use the official `org.opencv:opencv:4.12.0` Android AAR from Maven Central,
pinned in the version catalog. The OpenCV team recommends this distribution for
the standard modules: <https://opencv.org/opencv4android-usage-models/>.
API reference: <https://docs.opencv.org/4.12.0/javadoc/org/opencv/imgproc/Imgproc.html>.
The AAR includes Java bindings and native libraries; no hand-copied binaries or
desktop substitutes are introduced. The AAR has no standalone notice bundle, so
the upstream SDK's OpenCV license and complete third-party notice directory are
packaged as vision assets; provenance and the verified SDK digest accompany them.

`core:vision` owns all OpenCV dependencies and native objects. Its public adapter
boundary accepts borrowed `CV_8UC4` RGBA Mats; `api` makes those types available to
Android consumers. Model, physics and planner retain no Android/OpenCV dependency.
`BoardDetector.create(bounds)` explicitly initializes the packaged runtime and
fails if initialization fails. Call it once, then reuse the stateless detector.

Each synchronous detection converts RGBA to gray, applies a 5x5 Gaussian blur,
then Canny (50/150). Closed contours are approximated at 2% perimeter. Require
four convex vertices, 10..90% frame occupancy, at least two pixels from the frame
edge, shortest/longest side >=0.65 and absolute corner cosine <=0.35. These are
conservative heuristics for complete, near-square boundaries with modest
perspective, not learned classification or a guarantee of game accuracy.
Distinct plausible boundaries fail as ambiguous. Nearby duplicate edge contours
are grouped, and the largest boundary represents that group.

Corners are clockwise in original frame pixels. The minimum x+y corner starts
the list; scores within 2% of the shortest side break ties by y then x, so tiny
corner jitter near 45 degrees does not rotate normalization by 90 degrees.
Duplicate contours are matched across cyclic corner shifts. This is a screen orientation convention, not player
orientation; symmetric images cannot establish the latter. Caller-provided
physical `BoardBounds` supplies millimetres. No dimensions are inferred from pixels.

`BoardTransform` owns an analytic square-to-quadrilateral homography and its
inverse as private Double coefficients. It exposes original-pixel <-> board-mm
mapping without clipping and rejects invalid quadrilaterals and projective
horizons. This adapter precedes the shared axis-aligned `CoordinateTransform`;
that model contract is unchanged. `normalize` additionally warps pixels to an
owned square RGBA Mat with board bounds at 0..size-1 (size 2..2048).

Input Mats are never mutated, retained or closed. All temporary Mats/contours
are released in finally blocks, including failure paths. Returned geometry owns
immutable values, no pixels/native buffers. The caller must release each
normalized Mat. There is no background scope, queue or persistent native cache.
Cancellation is not intercepted. Native detection errors have an explicit outcome;
initialization/normalization errors propagate. No plausible fallback geometry.

## Limits and follow-up

Confidence is side-ratio times corner-orthogonality in [0,1], not calibrated
probability. Generic square UI panels can be false positives; use only an
authorized board viewport and validate against real labeled game fixtures before
using results for advice. Rails can compete with the inner playing boundary;
multiple sufficiently separated candidates are rejected, while nearby rail edges
can still bias dimensions. Strong perspective, occlusion, clipping, low contrast
and orientation changes near corner-score ties need further calibration/tracking.

This ticket supplies geometry only. Capture plane/padding conversion and live
pipeline wiring belong to CB-35; object/pocket detection and tracking are separate
tickets. Current app UI still counts frame metadata. Runtime/memory costs scale
with supplied frame pixels/contours; no real-time throughput or leak-free native
heap claim is inferred from the repeated-call smoke test.

Golden PNGs are original synthetic screenshot-like frames generated by the
checked-in standard-library Python script, never captured personal/game screens.
They define known corners with a 3px detector tolerance and a blue center marker
to check the image warp. Pure JVM tests check physical transform invariants.
Native device tests exercise the actual packaged OpenCV runtime. See
[validation](../validation-cb-21.md) for executed evidence and platform limits.
